Opening

LaunchRig is a developer tool for the failure boundary after a mobile wallet interaction. The current proof is a working local prototype on ordinary Android, not a claim of Seeker or production-wallet coverage.

02 / 10

The origin and the problem

The failure happens after the wallet says done.

I wanted to build for Solana Mobile without a Seeker, on a laptop that could not comfortably carry an emulator-heavy workflow. Testing on an ordinary USB-connected Android phone exposed the larger problem: successful authentication did not prove safe recovery from every mobile lifecycle path.

R01
User rejectionThe app must recover without a false success state.
R02
Stale authorizationThe session must renew or fail clearly.
R03
Process deathRecover to UNKNOWN and enable retry.

Founder story

This account comes from the actual build constraints: no Seeker, limited laptop resources, and an ordinary Android phone connected over USB. It makes no claim of prior user losses, employer experience, or a production incident.

The three cases are deliberately controlled fixture regressions. They are not defects found in an external publisher app.

Product workflow

The publisher supplies stable app flows. LaunchRig owns the Solana-specific validation, lifecycle matrix, artifact binding, run policy, and normalized output.

The HTML, JSON, and JUnit reports serve human review, machine checking, and CI. The normalized nine-report evidence package is public. Its standalone semantic verifier remains internal. Public checksums establish file integrity, not independent authenticity.

Why Solana Mobile

Android wallet handoff and recovery through MWA.

Established now

Ordinary Android + development fixtures

  • Reference and Mock MWA mobile wallet flows
  • Wallet rejection, stale authorization, and process-death recovery
  • Reference requests use testnet; controlled cases use devnet
  • Artifact identity, bounded logs, and offline verification

Proposed post-award

Actual Solana Mobile hardware qualification

  • Acquire or obtain separately permissioned Seeker access
  • Test production-wallet behavior as a distinct compatibility layer
  • Observe Seeker and Seed Vault-backed wallet behavior through MWA
  • Publish only separately permissioned, attributable results

MWA is the open app-to-wallet protocol on Android. Solana Mobile documentation directs dApp developers to MWA, while Seed Vault is primarily consumed through wallets. Sources: MWA and Seed Vault, checked 23 Sep 2026.

Stack fit

The current technical integration is MWA, which Solana Mobile documents as the open protocol connecting Android apps and wallets. Seed Vault is hardware-level key custody on Seeker and is normally reached by dApps through a wallet and MWA.

Seed Vault compatibility, production-wallet readiness, and Seeker validation remain explicit post-award qualification tasks. Observing a Seed Vault-backed wallet through MWA does not independently validate secure key custody. The current evidence does not establish on-chain execution.

Differentiation

LaunchRig complements Maestro, Appium, Firebase Test Lab, and Mock MWA as the contract and evidence layer around a mobile runner and wallet fixture.

Milestones

M1 converts the local foundation into a supported public contract and adds actual hardware qualification. M2 tests integration cost and usefulness with permissioned projects. M3 and M4 harden, document, and hand the tool to the ecosystem.

A pilot can succeed even if it finds zero defects. Acceptance measures completion, setup time, qualifying run time, maintenance cost, verification result, and sharing review.
